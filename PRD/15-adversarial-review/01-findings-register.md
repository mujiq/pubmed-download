# Findings Register

All 63 verified findings, grouped by review dimension. Each entry records the verdict (`confirmed` /
`partially-addressed`), the kept severity (blocker / major / minor, mapped to the `RMP-ACC-140` register per ADV-00 §2),
the affected modules, the Fortune-100 outlier scenario, **what the PRD already covers** (for `partially-addressed`
findings), the residual gap, the recommendation, and a status (`open` or `recommended-doc-change`). Gap claims are
stated against verified PRD text per `ADV-GOV-002`; the governing evidence lives in the review working notes.

**Status legend.** `open` = the gap stands and is unassigned; `recommended-doc-change` = the gap stands and a specific
module edit is proposed (and carried into ADV-REM). All 63 are currently `recommended-doc-change` — the review proposes
a concrete fix for each — pending DGC acceptance at the owning gate.

**Severity tally:** 0 blocker · 32 major · 31 minor · (17 confirmed, 46 partially-addressed).

## 1. Legacy, tech-debt & M&A (`ADV-LEG`)

### ADV-LEG-001 — No worked adapter or scope statement for a co-existing non-Cerner EHR
- **Severity:** minor · **Verdict:** partially-addressed · **Modules:** 00, 03, 06, 08, 13 · **Status:** recommended-doc-change
- **Outlier:** An acquisition brings Epic (plus a regional Meditech MAGIC/Expanse and a decade-old Soarian pending sunset). All must feed HEALIX clinical data for years during consolidation to Cerner.
- **What exists:** `03/README.md` §4.3–4.6 is a **vendor-neutral** Source Registry: `system_class: ehr`, an extraction taxonomy (`fhir_api` + `$export`, `cdc_log` for Clarity/Caboodle, `file_drop` for Meditech NPR/DR, `ccda_document`), a generic 12-step onboarding checklist, and design principle 3 (every source code system harvested as a `CodeSystem` — the Cerner `CODE_VALUE`/`NOMENCLATURE` pattern generalised). `06` FHIR R4 **is** the cross-vendor canonical layer. UX/self-healing/prototype modules already assume M&A legacy EHRs coexist (`16/02` SYN- merge over "merged or legacy EHRs"; `14/04` FLT-ING-015; prototype `St. Francis (M&A legacy)`).
- **Gap:** The capability is generic but there is (a) no *worked reference adapter* instantiating it for one non-Cerner EHR, (b) no explicit scope line in `00 §6` saying whether a second clinical EHR is in first-release scope (the scope matrix implies Cerner-only while other modules assume coexistence — an internal inconsistency), and (c) cross-EHR clinical entity resolution is deferred past Phase 1 (`16/02`) even though EMPI-collision self-healing (FLT-ING-015) assumes merged-facility identity work is live.
- **Recommendation:** Add one reference EHR adapter (e.g. Epic via `fhir_api`/`$export` + `CodeSystem` harvest of EAP/.1 masterfiles); add a one-line scope/non-goal in `00 §6`; pull cross-EHR entity resolution into a phased plan. No new ingestion spec is needed.

### ADV-LEG-002 — Local-terminology & source IRIs carry no Millennium-domain qualifier
- **Severity:** major · **Verdict:** confirmed · **Modules:** 03, 06, 08, 13 · **Status:** recommended-doc-change
- **Outlier:** Two+ Millennium domains coexist (common post-M&A, consolidation deferred for years). Domain A `CODE_SET 71 / value 309` = "Observation encounter"; Domain B same key = site-added "Hospice"; `NOMENCLATURE_ID 148822` differs per domain. All land under one URI family `urn:healix:cs:cerner:code-value|71`, silently conflating two concepts; facility mnemonics reused across builds collide in `id/patient/cerner/<facility>/<mrn>`.
- **Gap:** `03/01 §4.2`, SRC-CER-005/006, the registry example (`cerner-millennium-prod`) and TKG-03 blocking all assume one domain. `§4.2` overclaims `CDF_MEANING` as "stable across sites" — true only for Cerner-*seeded* meanings, not site-added values or domain-local `NOMENCLATURE_ID`s. The roadmap's "additional Cerner by configuration" (RMP-PH1-012, OQ-16) scopes only *facilities within one domain*, never a second domain/build. `14/04` already knows the estate is multi-domain (FLT-ING-015/016) but only operationally (tz offset, MRN adjudication, memory partitioning).
- **Recommendation:** Make source instance (domain) a first-class namespace component: `urn:healix:cs:cerner:<domain>:code-value|<set>`, `:<domain>:nomenclature`, and `id/patient/cerner/<domain>/<facility>/<mrn>`. Add a same-`(set,value)`/same-`NOMENCLATURE_ID` conflict-detection + reconciliation step; a facility-mnemonic uniqueness guard at IRI mint; and revise SRC-CER-005/006, RMP-PH1-012, OQ-16 to distinguish "facility within a domain" from "additional Millennium domain". *(Root-cause sibling of ADV-SEM-005 and ADV-INT-005.)*

### ADV-LEG-003 — Legacy ERP (EBS / PeopleSoft / Lawson) coexisting with Fusion: no SoR precedence or COA crosswalk
- **Severity:** minor · **Verdict:** partially-addressed · **Modules:** 03, 04, 05, 08 · **Status:** recommended-doc-change
- **Outlier:** Corporate on Fusion Cloud; two acquired entities still on Oracle EBS R12 on-prem; a legacy hospital on PeopleSoft/Lawson. HEALIX must consolidate GL/AP/suppliers/workers across all three during a multi-year window with divergent charts of accounts.
- **What exists:** `cdc_log` already covers on-prem EBS/PeopleSoft (Debezium/LogMiner/GoldenGate — `README §4.5/§4.7`); `system_class: erp|hcm|scm` already allows a second ERP with its own slug; onboarding step 2 explicitly handles "overlaps with existing sources"; cross-ERP code-system crosswalks are the Stage-3 thesaurus/ConceptMap job; TKG-03 §5.1 survivorship is a steward-owned YAML pack with configurable trust ranks.
- **Gap:** SoR is hard-coded to Fusion in prose — `03/02` opening line, `04/01:94`, `04/02:72` ("Oracle Fusion ERP primary"), and TKG-03 §5.1 illustrative rules ("Oracle Fusion only", "Oracle item master"). No requirement mandates a cross-ERP COA / natural-account crosswalk or multi-ERP SoR precedence.
- **Recommendation:** Parameterise the TKG-03 §5.1 survivorship packs to express configurable precedence across ERP sources (strike the absolute "Fusion is the system of record"); add a required Stage-3 cross-ERP COA / natural-account ConceptMap deliverable triggered when a second finance source registers; register each legacy ERP as its own `erp` source. No new extraction pattern or source model is needed.

### ADV-LEG-004 — Mainframe / COBOL / DB2 / VSAM batch is an error condition, not a first-class ingestion pattern
- **Severity:** major · **Verdict:** partially-addressed · **Modules:** 03, 06, 14 · **Status:** recommended-doc-change
- **Outlier:** Legacy patient accounting/self-pay, home-grown claims adjudication and payroll run on z/OS with DB2/VSAM, emitting nightly EBCDIC fixed-width files with COMP-3 packed-decimal amounts described by COBOL copybooks.
- **What exists:** The scenario is acknowledged — but *only* as a self-healing parse-failure (`14/04` FLT-ING-004 + recovery row "EBCDIC/fixed-width mainframe batch files (legacy claims, payroll)"), and the specified recovery is "code-page registration via mapping CR" after a quarantine.
- **Gap:** `03/README §4.5` `file_drop` is "CSV/Parquet/fixed" with raw bytes and no copybook/EBCDIC/COMP-3 handling; the only relational CDC is Debezium on the Millennium replica (no z/OS DB2 connector — Debezium has none). The specified "guess the code page and re-parse" is operationally wrong: EBCDIC code pages (CP037 vs CP1047 vs CP500) cannot be inferred and COMP-3 is binary, so re-parsing silently corrupts financial amounts — a revenue-integrity risk, hence major not minor.
- **Recommendation:** Add `copybook_fixed` and a DB2-z change-capture pattern to §4.5; register the COBOL copybook as a first-class SRC-REG artifact (offsets, PIC, COMP-3 sign nibble, OCCURS DEPENDING ON, REDEFINES); declare the source code page in the interface record and transcode deterministically at ingest (never infer); treat COMP-3 money as parse-or-fail; name a real z/OS DB2 CDC channel (IBM IIDR / Q Replication, or GoldenGate for DB2 z/OS); rewrite FLT-ING-004 to reference the deterministic contract. *If* the org mandates upstream ASCII transcoding before HEALIX, downgrade to a stated ingestion assumption — but state it.

### ADV-LEG-005 — Charge Description Master: no effective-dated list-price reference and no charge-code DQ
- **Severity:** minor · **Verdict:** partially-addressed · **Modules:** 03, 05, 08, 09 · **Status:** recommended-doc-change
- **Outlier:** Post-merger the same CT-with-contrast carries charge `4512300` at the legacy facility and maps to CPT `70491` differently at the main campus; the enterprise CDM rebuilds annually (retiring/renumbering codes) and reprices quarterly; cost-to-charge analytics need the price in effect on the service date.
- **What exists:** The CDM is routed through the full versioned-code-system + concept-map + golden-entity machinery: loaded as a G8 code system (`dim_code`/`ref_concept` with `effective_from/to`, `concept_status active/inactive/retired`, release versioning); Cerner `BILL_ITEM` CDC is bitemporal (08-01 §5.3); supply/drug charges resolve to a golden Item (08-03 §1, `bridge_cdm_item`); posted price-on-service-date is preserved in `fact_charge.unit_price_amount`/`extended_amount` (bitemporal); charge↔AR/GL reconciliation exists.
- **Gap:** (1) No CDM/CPT **list price** modeled as effective-dated reference data (no `dim_charge_master` with price × effective period × gross-charge-to-cost ratio; no `price-as-of(service_date)` lookup) — cost-to-charge analytics can only read the price that *posted*. (2) No DQ rule validates `fact_charge.charge_code_src` against the effective-dated CDM (the existing retired-code rule targets CPT/HCPCS claim lines). (3) Service (non-supply) charges have no golden "ChargeableService" survivorship key.
- **Recommendation:** Add a versioned/effective-dated CDM price reference in G8 with as-of lookup; add `DQR-VALIDITY-CHARGE-*` for unmapped/retired/renumbered charge codes on the service date; make the order-catalog→CPT crosswalk the explicit survivorship key for merged-facility service charges. Drop the CDM-versioning/retired-code/supply-reconciliation parts — already covered.

### ADV-LEG-006 — No one-shot historical-migration source pattern or read-only-archive option for decommissioned systems
- **Severity:** minor · **Verdict:** partially-addressed · **Modules:** 03, 05, 08 · **Status:** recommended-doc-change
- **Outlier:** An acquired hospital's Soarian is decommissioned; 12 years of encounters/results/charges load once with real-world valid-time in the past, transaction-time = migration date, lower-trust provenance — or stay in a read-only archive (MediQuant-class) HEALIX references rather than ingests. No live feed follows.
- **What exists:** The hard machinery is present — `change_reason_code` includes `reload`/`late-arrival`; `valid_from` from source, `recorded_at` from loader (EDW-HIST-004); restartable bulk load (TKG-STORE-004, ≥200M triples/h); isolable droppable backfill named graphs (TKG-INGEST-016); mandatory provenance on every row (DQR-COMPLETENESS-PROV-001).
- **Gap:** (1) No `historical_migration` extraction pattern / registry lifecycle for a load-once, never-active, no-live-feed source (`active` presumes a deployed connector). (2) Survivorship has no "migrated-legacy" tier and no default precedence for an unranked source, so a 12-year-old Soarian value's survivorship is undefined and could silently beat current Cerner. (3) No module mentions a read-only active-archive (MediQuant/Olah-class) as a supported migrate-vs-reference option.
- **Recommendation:** Add the `historical_migration` pattern + lifecycle; add an explicit rule that migrated/decommissioned sources rank below live systems with a defined default precedence; document the migrate-vs-archive decision and a KG stub/pointer pattern. Drop the proposed migrated-records prov-completeness DQ rule as redundant with DQR-COMPLETENESS-PROV-001.

### ADV-LEG-007 — Blank/colliding HL7 assigning authorities from acquired facilities trigger wholesale quarantine
- **Severity:** major · **Verdict:** confirmed · **Modules:** 03, 06, 08, 09 · **Status:** recommended-doc-change
- **Outlier:** A newly acquired facility's interface engine emits PID-3/PV1-19 with empty/defaulted CX-4, or two facilities both emit `...^^^^MR` with overlapping ranges. Under SRC-CER-016 / IOP-V2-011 / SRC-PER-035 every such message fails std validation or is withheld from canonical, so the whole feed is quarantined on day one of onboarding.
- **Gap:** The strict reject/quarantine is safe for a clean single-domain feed but has no governed inference-and-review escape valve. No per-`(source,facility)` default assigning authority, no MSH-4 fallback, no assigning-authority-collision DQ rule. The PRD assumes this world (prototype `FAC-ONC "...(acquired)"`; TKG-03 opens on "three MRNs across facilities") yet blocks onboarding rather than inferring-and-reviewing.
- **Recommendation:** Add an optional steward-approved per-`(source_id, facility)` `default_assigning_authority` to the Source Registry (`03/README §4.3`, onboarding step between 5 and 7); when CX-4 is blank, namespace with it (Provenance note + DQ flag) instead of failing — inference permitted *only* when a steward-approved default exists, else still quarantine. Add a DQ collision rule and route suspected collisions into the TKG-03 §8 review queue. Until built, acquired feeds with unpopulated CX-4 require the integration team to populate the authority upstream (the current de-facto workaround).

## 2. Scale & performance (`ADV-SCALE`)

### ADV-SCALE-001 — KG triple-count and store sizing are mutually contradictory and never reconciled
- **Severity:** major · **Verdict:** confirmed · **Modules:** 08, 12 · **Status:** recommended-doc-change
- **Outlier:** A 10+ hospital system accrues the required 10 B triples; annotations (lab amendments, claim resubmissions, EMPI merges) accrete as RDF-star triple-terms.
- **Gap:** Three growth figures disagree and nothing reconciles them: `08/02 §1/§3` requires ≥10 B triples (≈2 B base + ≈8 B annotation) and TKG-STORE-002 restates 10 B + 50 M named graphs; `08/02 §3`'s own arithmetic ("2.5 B/month, ~70% dedup → near 10 B over 5 yr") does not reconcile (~9 B/yr net implies ~45 B); `12/01 §5` sizes the store at "5 B triples" headroom and lists "1.2 B triples/year". No module sizes index overhead, replica factor or hot working-set for the 10 B requirement.
- **Recommendation:** Publish ONE authoritative KG growth model (08 §3), self-consistent (base + annotation/yr with an explicit correction/supersession multiplier and the post-dedup net rate); correct the OPS-01 §5 driver (`1.2 B/yr`) and headroom label (`5 B`) to match TKG-STORE-002 (or revise TKG-STORE-002 if the true target is lower); add a measured bytes-per-triple-with-full-index sizing for the chosen product with replica factor and hot working-set; run the §8.2 conformance load on hardware sized from that model. Drop the unsupported claims that 8 TB NVMe cannot hold 10 B. *(Reframed from blocker: a sizing-reconciliation defect, not a hardware-can't-hold-it claim.)*

### ADV-SCALE-002 — "5,000 resources/s" is used as sustained floor, sustained sizing basis AND peak ceiling
- **Severity:** major · **Verdict:** confirmed · **Modules:** 01, 07, 12 · **Status:** recommended-doc-change
- **Outlier:** Capacity review for a 6-hospital estate: the Kafka estate is built to 180 MB/s (5,000/s × 3) while the deployment table says real sustained is ~600/s (50 M canonical/day ÷ 86400 = 579/s), and the morning-rounds peak is never derived bottom-up.
- **Gap:** The same number means three things, all citing ARC-NFR-002: sustained floor (`01/ARC-NFR-002`), sustained sizing basis (`07/01 §1.2`, STR-TOP-003 "3× the sustained canonical throughput"), and peak ceiling (`12/01 §5` `sustained 600/s, peak 5,000/s`; Flink "burst to peak 5,000/s"). Applying §1.2's own ×4 morning factor to a true 600/s gives 2,400/s, not 5,000/s — the peak is back-fit to the headline, not computed. Direction of risk is over-provisioning (cost), but autoscale ceilings (Flink 24–96 TMs, 5,000 `$translate`/s) rest on an unanchored number.
- **Recommendation:** Adopt the two-number model: sustained ≈600/s (derived) and a peak derived bottom-up (per-source peaks → canonical) at the real facility count; rewrite ARC-NFR-002 to name both with headroom against each; re-key `07/01 §1.2` "Basis" and STR-TOP-003 to the reconciled peak (document the 180 MB/s estate as headroom over a derived peak, not 3× of sustained); re-anchor the Flink and Terminology autoscale ceilings. Note it is a correctness/cost/consistency fix, not urgent under-capacity.

### ADV-SCALE-003 — Nightly EDW load window & EDW↔KG reconciliation at multi-timezone scale
- **Severity:** minor · **Verdict:** partially-addressed · **Modules:** 05, 08, 12 · **Status:** recommended-doc-change
- **Outlier:** 10+ hospitals span several time zones; "completed by 06:00 local" is ambiguous and the overnight window is compressed by the easternmost sites while a nightly reconciliation scans multi-billion-row facts.
- **What exists:** The architecture is a single centralised streaming-first MPP EDW (not a warehouse per hospital), so there is no per-site load window to compress. Reconciliation is already transaction-time-day-scoped (TKG-04 §7.2: content hash over `assertions recorded on D`, at fixed 02:00 UTC) — i.e. the "make it incremental" fix is already implemented. `COLLECT STATISTICS` fires only on batches >1% of rows, far above a daily increment (EDW-PHY-005). EDW-REC-003 blocks promotion only for a table *touched by the release*. Current-view graphs are ~15% of triples, incrementally maintained.
- **Gap:** Only spec-precision nits remain: "06:00 local" is undefined for a two-region EDW; and the daily content hash covers only day D with an all-history counts-only check, so a silent historical-row hash drift that doesn't change counts could be missed.
- **Recommendation:** Define the freshness anchor (S11/OPS-SLO-005/EDWBatchLate) explicitly in UTC for the enterprise region; add a short capacity note (or make the uat/prod soak gate explicit as the budget) for the ~1.5 B-triple current-view rebuild; add a periodic (e.g. weekly) full content-hash sweep. Drop the full-scan-XOR / statistics-burden / per-site-window claims — not real for this architecture.

### ADV-SCALE-004 — Agent/CR & token budgets sized for steady state, not the M&A onboarding/backfill surge
- **Severity:** minor · **Verdict:** partially-addressed · **Modules:** 06, 10, 12, 13 · **Status:** recommended-doc-change
- **Outlier:** Onboarding an acquired hospital = a fresh Millennium domain's `CODE_VALUE`/`NOMENCLATURE` plus a 10 M-resource FHIR backfill; each previously-unseen local code raises a `terminology_steward` CR and each mapping failure a `source_mapper` CR — many thousands over the 14-day backfill, far above the 2,000 CRs/day steady-state the caps were sized for. When a per-agent daily token cap is hit, non-P0 CRs pause — stalling exactly the mapping CRs the backfill depends on.
- **What exists:** Compute autoscale 0–200 pods ("burst 10×"); C0–C4 caches explicitly built to "absorb bursts (a Cerner CODE_VALUE surge)"; onboarding staged 1→2→all (OQ-16) and lands in uat first; rich surge handling at the detection layer (FLT-SEM-002 P0 + PBK-SEM-001, `code_surge_signature` memory). RMP-RISK-012 deliberately forbids relaxing auto-approval under queue pressure.
- **Gap:** No bounded onboarding/backfill CR-volume model separate from the 2,000/day steady state; no per-CR token estimate; no surge/backfill budget class; and the pause-non-P0 hard limit plus the rule that budget raises are human-only (`14/04` policy class) means the autonomous recovery path is blocked during exactly this window.
- **Recommendation:** Add a bounded onboarding CR-volume model and per-CR token estimate (the cost-per-CR metric in `12/03 §201` gives the basis); a declared, time-boxed, operator-signed "onboarding/backfill budget class" lifting the per-agent cap for `terminology_steward`/`source_mapper`; change the hard-limit default during a declared onboarding window so mapping/terminology CRs are not in the paused set. Do NOT relax auto-approval (RMP-RISK-012) — use steward-capacity surge + proposal batching + the budget exemption.

## 3. PHI & security edges (`ADV-PHI`)

### ADV-PHI-001 — Adolescent minor-consent confidentiality & parent/guardian proxy access unmodeled
- **Severity:** major · **Verdict:** partially-addressed · **Modules:** 11, 06, 03, 16 · **Status:** recommended-doc-change
- **Outlier:** A 15-year-old is seen for STI, contraception and a behavioral-health visit under state minor-consent law; the parent holds a Cerner proxy relationship and a portal proxy account and MUST NOT see those encounters while still seeing routine pediatric data. At 18 the proxy must auto-terminate.
- **What exists:** `GOV-01 §3` already segments and consent-gates reproductive and mental-health data by role/purpose (two of the three example services); `§9` jurisdictional overlays cover state CMIA/HIV/genetic/reproductive-shield; SRC-PER-020 already models proxy as FHIR Consent + RelatedPerson in G1/G9 — but only for outreach consumers, and Cerner event-level confidentiality (`CLINICAL_EVENT.CONFID_LEVEL_CD`) already feeds `meta.security`.
- **Gap:** The specific case is absent: a proxy principal authorized for routine peds data but denied the minor's confidential-service encounters, keyed on patient age + minor-consent service type, with age-of-majority revocation. GOV-02 identity has no patient-age ABAC attribute and no proxy/RelatedPerson-authorized launch concept; GOV-01 §5 has no minor/proxy consent-gate row.
- **Recommendation:** Wire up existing primitives — add patient age bracket / minor-status as an ABAC object attribute (keyed off facility+state); add a GOV-01 §5 "adolescent minor-consent confidentiality" gate that suppresses minor-consent-service encounters from a proxy principal; extend GOV-02 to recognise a proxy/RelatedPerson launch and treat the proxy as a distinct gated principal; model age-of-majority auto-revocation as a bitemporal JML event; add a privacy_guardian rule and a module-03 mapping of Cerner `PERSON_PERSON_RELTN`/`ENCNTR_PRSNL_RELTN` + encounter confidential flag. Correct the finding from "entirely unmodeled" to "proxy for outreach only; adolescent-confidentiality suppression and age-of-majority revocation absent."

### ADV-PHI-002 — Retained C-CDA / document blobs bypass sensitive-category segmentation on outbound (no DS4P)
- **Severity:** major · **Verdict:** partially-addressed · **Modules:** 06, 11, 12 · **Status:** recommended-doc-change
- **Outlier:** A CCD/Discharge Summary stored as monolithic XML contains, in one document, a routine problem list plus a behavioral-health note, a positive HIV result and a MAT/SUD (Part 2) med; a partner runs Patient-level `$export` or fetches the `DocumentReference` attachment.
- **What exists:** The governing policy exists (GOV-PHI-005 segmentation; GOV-PHI-010 "Part 2 MUST NOT leave the originating segment without matching Consent + re-disclosure notice"), and `$export` IS gated (IOP-FHIR-108, HIE opt-out covers "outbound FHIR Bulk Data"). The XCA-CrossGatewayRetrieve-*from-HEALIX* framing is out of scope — the PRD never makes HEALIX an outbound XCA responder (it is a consumer/initiating gateway).
- **Gap:** GOV-PHI-005/010 enumerate enforcement only on Kafka headers, KG named graphs and EDW RLS — the retained object-store blob (C-CDA XML, externalised OBX-5 ED/pathology PDFs) is outside all three; no **document-level sensitivity is computed from content** (`confidentialityCode` is source-asserted and whole-document); the object-store attachment fetch path is gated only by DSA data-use terms, not the per-record sensitive-category consent PDP.
- **Recommendation:** Compute and stamp a document-level sensitivity label (max of extracted-resource `meta.security` + NER over narrative) onto `DocumentReference.securityLabel` at ingest; enforce the consent/sensitive-category PDP at the object-store proxy on every attachment fetch; suppress or DS4P-redact sensitive-category sections before outbound release; confirm de-identified `$export` (GOV-PHI-014) actually processes the monolithic blob, not only discrete resources. Drop the XCA-responder framing (raise separately if a responder role is ever intended).

### ADV-PHI-003 — No relationship-based snooping/VIP detection; VIP flag undefined at the access boundary
- **Severity:** major · **Verdict:** confirmed · **Modules:** 11, 08, 10 · **Status:** recommended-doc-change
- **Outlier:** An analyst/steward/researcher reads a single chart — ex-spouse, coworker-as-patient, neighbor, admitted celebrity. One authorized read, no volume/PHI-class deviation, trips no alert — the canonical HIPAA snooping case Protenus/FairWarning exist to catch.
- **Gap:** Detective controls are purely volume/distribution-based (GOV-03 §5.3 SIEM: impossible travel, bulk reads, after-hours; privacy_guardian: baseline deviation) and catch no single targeted lookup. No relationship-based detection (same surname/address, employee-record match, declared relationship, self-access, VIP). The "VIP flag" appears only as a TKG-03 §8 ER auto-link veto — never sourced as a patient-level flag, never a PDP attribute, never a heightened-audit obligation. privacy_guardian carries `phi_access: none` so it structurally cannot do this. (Event-level confidentiality `CONFID_LEVEL_CD → meta.security` already exists — the gap is patient-level VIP + targeted-access detection, not confidentiality labelling.)
- **Recommendation:** Add a relationship-based / targeted-single-access monitoring control over `hc.ops.audit.v1` for HEALIX's own consumer surfaces (FHIR facade, EDW secure views, SPARQL proxy) detecting same-surname/address, Oracle HCM employee match, declared family/proxy, self-access and VIP accesses on even one read; define a sourced patient-level VIP/confidential-patient flag as a PDP attribute driving masking + mandatory heightened audit. State the scope boundary: whether live Cerner PowerChart logs flow into `hc.ops.audit.v1` (the classic bedside case) or remain an EHR-layer tool.

### ADV-PHI-004 — 42 CFR Part 2 re-disclosure obligation does not travel to EDW rows, aggregates or the claims path
- **Severity:** minor · **Verdict:** partially-addressed · **Modules:** 11, 05, 06, 08 · **Status:** recommended-doc-change
- **Outlier:** A MAT (buprenorphine) med and a Part 2 encounter generate a charge → 837 claim and feed a G6 "patients on MAT" measure; the re-disclosure notice GOV-PHI-010 pins to `meta.security` is absent from the EDW charge row, the aggregate and the outbound 837.
- **What exists:** The "only in meta.security" framing is overstated — Part 2 is segmented per-record on Kafka (`hc-part2-flag`), in the KG (segmented named graphs + graph-level `phiClassMax` ACL) and in the EDW (RLS `part2_flag`, consent-directive filtering, deid-view filtering); `§5` requires an active matching Consent for ANY SUD flow beyond the originating program, enforced in Flink and again at the consumer boundary. That is substantive segmentation.
- **Gap:** Three narrow edges remain: (1) derived aggregates/extracts (G6) do not inherit/taint Part 2 provenance, and small-cell suppression is a de-id control, not Part 2 segregation; (2) the outbound X12/837 path has no Part 2 consent gate or restriction indicator (X12 has no `meta.security` analogue; RCM owns the claim); (3) Part 2-specific accounting of disclosures is not distinguished from HIPAA/TPO accounting (GOV-LIN-011).
- **Recommendation:** Make G6 aggregates over Part 2 rows inherit a provenance marker or release only via a governed de-id transform; apply the §5 Part 2 gate + restriction indicator to the outbound 837 generator (IOP-X12-012) and clarify the RCM-owned control boundary; define Part 2-aware accounting of disclosures. Treat the internal segmentation as already adequate.

### ADV-PHI-005 — Consent revocation reconciliation vs the bitemporal store, compacted snapshots and as-of queries
- **Severity:** major · **Verdict:** partially-addressed · **Modules:** 11, 08, 07, 12 · **Status:** recommended-doc-change

### ADV-DQ-006 — Aggregate-sum reconciliation masks offsetting errors and mishandles signed amounts

### ADV-OPS-002 — Blue/green of exactly-once Flink jobs is under-specified (transactional.id fencing; shadow writes to live topics)
- **Severity:** major · **Verdict:** confirmed · **Modules:** 07, 12 · **Status:** recommended-doc-change
- **Outlier:** An engineer deploys a new `proc.canonicaliser` blue/green from a savepoint during quarter-end; green uses EXACTLY_ONCE with `transactional.id.prefix=proc.canonicaliser.` and writes to the same `hc.canonical.*` topics as blue.

### ADV-TMP-001 — UCUM conversion is a scalar factor+offset with one canonical unit per dimension; mass↔molar / IU values are wrong or silently incomparable
- **Severity:** major · **Verdict:** partially-addressed · **Modules:** 05, 06, 03 · **Status:** recommended-doc-change

An analyst trending across the two labs, or a measure summing a LOINC, gets numerically wrong, non-comparable values with no error.
- **What exists:** `value_numeric_src` + `unit_src_text` are always retained (EDW-G2-003), and the PRD DOES mandate analyte-aware conversion ("mg/dL ↔ mmol/L per analyte table", "never for drug doses", "unit conversion MUST use `ref_unit_conversion`" — 09/05). - **Gap:** `ref_unit_conversion` is referenced in prose but defined in NO DDL (not in `g8_reference.sql`), with no molar-mass/substance/LOINC-key columns; `dim_ucum_unit`'s per-dimension scalar factor physically cannot bridge mass↔molar; `[IU]`/`[arb'U]`/`U/L`/katal appear nowhere; and DQR-ACCURACY-OBSERVATION-005 inner-joins the plausibility range on `(loinc, ucum)` so a value in an unexpected unit is excluded from the fail set and silently passes.
- **Recommendation:** Define `ref_unit_conversion` in G8 DDL keyed by observation/substance (LOINC + molar mass / UNII) with `source_ucum → loinc_preferred_ucum` factor, and wire fact canonicalisation to it (reconcile which table produces `value_numeric`); add a non-convertible marker for IU/arbitrary/enzyme-activity assays so they are never folded; add the two DQ rules (quarantine a source unit not in the allowed set for its LOINC; detect multiple unit systems for one LOINC across sources). Drop the drug-dose portion. *(Reframed from blocker: raw preserved, intent documented, but `ref_unit_conversion` unbuilt + silent cross-unit comparison.)*

- **Severity:** major · **Verdict:** partially-addressed · **Modules:** 05, 08 · **Status:** recommended-doc-change

- **What exists:** The seat/scope obligation is stated (99 §8) and the agent-as-licensed-user question is posed (HCDM OQ3) — but only for the HCDM model document, not the clinical terminologies the fleet consumes; licence handling is display filtering (ONT-GOV-009) + a seat-ACL vault for the UDMH/HCDM *models* (RDM-UDMH-002); the BAA register tracks vendor agreements but not terminology seat entitlements/usage.
- **Gap:** No terminology-licence entitlement register, no metering of TS consumption per licensed system, and no generation of the SNOMED-affiliate / UMLS-annual / CPT seat-and-usage report the licences require (the UMLS annual report is a hard obligation the platform currently cannot satisfy); the agent-as-user question is unresolved for CPT/SNOMED.
- **Recommendation:** Add a terminology-licence entitlement register in G9 (parallel to `ref_business_associate`) per code system (licence class, seat/scope entitlement, licensed human roles AND agent identities, UMLS annual re-acceptance dates); extend the TS gateway's write-audit (IOP-TS-026) to meter read ops by licensed system + distinct consumer; add a scheduled governance artefact generating the UMLS annual / SNOMED affiliate / CPT seat report; and — cheapest and most important — generalize HCDM OQ3 to an explicit Legal/IP determination of whether an autonomous agent is a "licensed user" for CPT and SNOMED/UMLS, resolved before agents consume licensed displays in prod (a Phase-1 gate). Severity is driven mainly by the mandatory UMLS annual report; if Legal returns "enterprise licence, not per-seat," the CPT-seat parts scale down to metering + annual report.

### ADV-SEM-004 — No competency-question coverage metric or add-a-CQ-when-you-add-a-class rule; CQ pass-rate decays
- **Severity:** major · **Verdict:** confirmed · **Modules:** 02, 13 · **Status:** recommended-doc-change
- **Outlier:** Over five years hundreds of CR-OWL-CLASS/PROPERTY changes add G3/G4/G6 classes and new groups while the registered CQ set stays CQ-01..CQ-20. Each release reports "CQ pass rate ≥90%" (green forever, denominator is "registered"), while the fraction of classes/properties exercised by any CQ falls below a few percent, and a whole subsystem (e.g. revenue-cycle adjudication) can be semantically wrong with no CQ touching it. CQs run on a static fixture graph, so even the 20 cannot detect production-data drift.
- **Gap:** The CQ gate measures pass-rate over a FROZEN registered set with (a) no coverage metric (% of classes/properties/axioms exercised by ≥1 CQ), (b) no requirement that a CR adding/materially-changing a class/property register a CQ, and (c) no execution against production KG samples. The pass-rate denominator ("÷ registered") is mathematically non-decreasing. (The "subsystems undetectably wrong" blast radius is tempered: SHACL-conformance-on-24h-production-sample, axiom-derived shapes and nightly drift/reconciliation already guard production, and binding/element/FHIR/SHACL coverage gates scale with the ontology — so CQs are a secondary cross-domain layer.)
- **Recommendation:** Add a CQ-coverage release-gate metric alongside pass-rate (% of released classes/object-properties referenced by ≥1 CQ; 100% for G2/G3 top-level classes) — computable now from the "CQs touching it" mapping in 07 §2; make CR-OWL-CLASS/PROPERTY require an accompanying CQ (or a recorded Lead-Ontologist waiver) before approval. Running CQs against a de-identified production sample is a nice-to-have, not the primary fix. Frame as "the CQ metric is trivially satisfiable and decays over multi-year growth," not "subsystems can be undetectably wrong."

### ADV-SEM-005 — Polyhierarchy, axiom/class growth and reasoner runtime have no hard release gate
- **Severity:** minor · **Verdict:** partially-addressed · **Modules:** 02, 14, 12 · **Status:** recommended-doc-change
- **Outlier:** A decade of CRs (SNOMED attribute reuse, new groups, ERP extension families, polyhierarchy facet by facet) grows the enterprise OWL module past the reasoner's practical envelope; the nightly HermiT consistency run on `enterprise` no longer finishes, surfacing as FLT-SEM-004 (SEV3, manual) — a 3am incident rather than prevented at proposal time, and because consistency is a hard release gate, releases stall.
- **What exists:** Polyhierarchy ratio is measured (`≤15% per scheme, report-only beyond`), reasoner run time is monitored (`12/03`), class/property counts are exposed (GET /ontologies), FLT-SEM-004 catches timeouts reactively, and the EL-profile modularisation (05 §2) deliberately keeps ELK modules small — ELK on OWL 2 EL is polynomial and scales past SNOMED CT, so EL modules timing out is unlikely; the genuine tractability risk is the HermiT DL modules and the enterprise nightly run.
- **Gap:** No preventive release gate on reasoner classification/consistency RUNTIME, per-module axiom/class growth, or polyhierarchy breaching its threshold (it is report-only, no escalation/block).
- **Recommendation:** Promote the measured polyhierarchy ratio from report-only to an escalation that opens a refactor-review CR (not a hard block, to avoid jamming the cadence); add a per-module reasoner wall-clock budget as a release-gate WARNING forcing modularisation review, scoped to the HermiT DL modules + enterprise nightly run; add a per-module axiom/class growth delta on each release diff triggering architecture review past a threshold; re-validate the DL-module modularisation at each major release. Turning existing metrics into gates/escalations, not new infrastructure.
