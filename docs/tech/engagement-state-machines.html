Engagement State Machines — nudges, check-ins, self-reports & adherence

The four engagement artifacts PureScore creates and consumes every day are each a persisted state machine with explicit technical states, guarded transitions, timeouts, retries and terminal states. This page models all of them — the nudge (Doc 11), the check-in, the self-report (Doc 07, Doc 06) and the adherence check that closes the calibration loop (Doc 13).

Reading the diagrams
Each box is a persisted status. Solid edges are transitions within one machine (labelled with their trigger; full guards and side-effects are in the table under each diagram). Dashed edges in the overview are hand-offs to another machine or subsystem. State colours: green = adherent / ingested success, amber = in-flight / waiting, red = dropped / failed / missing, and an alert tint marks states that hand off to safety (Doc 16). All states are auditable and every transition is append-only logged.
Illustrative
State names, enums and window/TTL defaults below are a design model, not a shipped schema — they must be reconciled with the production event model and re-verified before any clinical or production use (README §5.6).

0 · Overview — how the four machines interconnect

The engagement layer is a closed loop: the engine emits nudges, the patient acts, adherence is verified, and the realized outcome recalibrates the next day's nudges. Check-ins and self-reports feed scoring (and, on red flags, safety) which in turn re-derives the engine's inputs.

2 · Check-in lifecycle

A check-in is a prompted capture on a cadence — a daily mood/symptom tap, a weekly review, or a scheduled PRO instrument (PHQ-9, GAD-7, ISI; Appendix C). Its technical job is to open inside a window, chase a response, validate and score it, route red-flag items to safety, and either ingest the result or record a defensible missing state that widens uncertainty rather than guessing.

3 · Self-reported data lifecycle

A self-report is unprompted patient-volunteered data — a logged meal, a "bad night", a home BP or weight, a medication taken. Its distinctive technical states are offline capture / sync, idempotent de-duplication, plausibility validation, a provenance / trust-tier tag (self-report carries lower confidence than device or lab; Doc 06, Doc 07), and being superseded when an authoritative source arrives.

4 · Adherence-check lifecycle

An adherence check verifies whether a recommended action was actually done — it turns a nudge completion into a calibrated outcome. It collects evidence (self-attestation, objective sensor corroboration, or none), resolves contradictions, scores an outcome, and feeds the per-patient adherence model p̂_a (Doc 11 §3.2, Doc 13). Repeated non-adherence re-strategises future nudges.

5 · Cross-machine technical invariants

The four machines share a small set of engineering rules that make the loop safe and replayable:

InvariantApplies toRule
Idempotencyallevery external event carries a key; re-delivered events are no-ops (duplicate sends, double submits, replayed syncs)
Timeout / expirynudge TTL, check-in window, adherence windowa clock transition always exists to a terminal state — no machine waits forever
Retry with capnudge delivery, check-in remindersbounded retries, then degrade to a terminal/failed state; never infinite loops
Absence ≠ valuecheck-in Missed, adherence Lapsed/Unverifiablemissing data widens uncertainty (Doc 05) and never imputes a favourable value
Provenance & trustself-report, adherence evidenceevery ingested datum keeps source + trust-tier + confidence; lab > device > self hierarchy on conflict
Safety pre-emptioncheck-in, adherencered-flag / disputed-harm transitions hand off to safety (Doc 16) and can override the normal flow
Append-only auditallevery transition is logged with actor, timestamp and reason; state is reconstructable for governance
Closed loopnudge → adherence → calibration → enginerealized outcomes refit p̂_a and impact estimates, so tomorrow's top-5 reflects what this patient actually does

Related: the data-stream states a whole patient can occupy live in the Patient state machine; the scoring response to these events is animated in the live feedback-loop demo.
