Wearable Baseline Pipeline · Terra · HealthKit · device clouds → one fool-proof baseline

How raw wearable data from Terra, Apple HealthKit, Google Health Connect and vendor cloud APIs (Oura · Whoop · Garmin · Fitbit · Withings · Dexcom · Libre) is ingested, validated, unified, transformed to canonical units, and turned into a robust personal baseline that drives the mobile baseline UI and the personal z-score (Doc 03 §2b, κ_resp). Every way the data can be wrong, late, duplicated or mis-united is a typed rule with a build-time completeness guard. Single sources: data/wearable-metrics.json · baseline-sources.json · baseline-formulas.json · baseline-dq-rules.json.

Illustrative
All bands, weights and cut-points on this page are literature/guideline-anchored examples and must be re-verified and cohort-adjusted before any production use (Conventions §5.6). This is design documentation, not a validated medical device.

Merge policy — same metric, many sources
  1. 1. TRUST TIER — clinical-grade (CGM, cuff, ECG, HSAT) > consumer-validated (Watch/Oura/Whoop) > inferential (sleep stages, VO₂max est.)
  2. 2. NATIVE RESOLUTION — within a tier, prefer the higher native sampling rate / finer granularity
  3. 3. RECENCY — prefer the freshest non-stale sample; older confirmations raise confidence, conflicts lower it
  4. 4. DE-DUPLICATE — collapse overlapping time intervals (steps, sleep) to a single source per interval before aggregating
  5. 5. NEVER POOL non-comparable definitions (SDNN≠RMSSD, absolute≠deviation, vendor scores) — keep separate series, choose one canonical

Conflict: When two trusted sources disagree beyond a metric-specific tolerance, take the higher-trust source, FLAG the conflict, and lower Confidence; never silently average across incompatible definitions.

Robustness contract — absorbing upstream change
  • SCHEMA TOLERANCE — unknown/new fields are ignored, never fatal; missing expected fields degrade gracefully to 'absent', not error.
  • VERSION PINNING — record the source schema version with every sample; a version change triggers a re-validation pass, not silent ingestion.
  • VALIDATION GATE — every inbound sample passes type/unit/plausibility validation (see baseline-dq-rules.json) BEFORE it can touch a baseline; rejects are quarantined + logged, not dropped silently.
  • UNIT GUARD — a sample whose unit can't be resolved to the canonical unit is quarantined (never assumed).
  • IDEMPOTENT INGEST — every sample carries a stable source id; re-delivered/duplicate payloads are no-ops (handles webhook replays + backfill).
  • CANARY/RECOMPUTE — baselines are recomputable from the immutable raw store; a discovered upstream bug is fixed by reprocessing, not patching baselines in place.
  • PROVENANCE — every baseline keeps the source, device, unit, schema-version and transform of each contributing sample, so any corruption is traceable and reversible.

3 · Baseline formulas

Each computed baseline = {center μ, spread σ_robust (1.4826·MAD), n_effective, last_updated, confidence, drift_slope}. Personal z = (x − μ)/σ_robust; the UI 'band' = μ ± k·σ_robust; 'deviation scan' = today's z per metric; 'drift' = center over time.

FamilyDefinitionWhenRobustness
Rolling mean / SDμ = mean(window), σ = sd(window) over a fixed N-day window.well-behaved, low-outlier metrics; baseline only.low — one bad day shifts μ and inflates σ.
Rolling median + MADμ = median(window), σ = 1.4826·MAD(window).default centre/spread — resists spikes (illness, travel, bad reads).high — ~50% breakdown point.
Exponentially-weighted moving averageμ_t = α·x_t + (1−α)·μ_{t−1}, α from a half-life.responsiveness layer — adapts to genuine physiological shifts (training, recovery).medium — bounded by clamping x_t to a plausible band first.
Robust + adaptive (DEFAULT) defaultcentre = blend(rolling_median, ewma_of_winsorized); spread = 1.4826·MAD; updates only with validated, de-duplicated, plausibility-passed samples.the canonical baseline for most consumer metrics.high + responsive.

Default per group: individual robust_median_mad + log_transform if skewed; context-conditioned if regime-dependent (BP morning vs evening). · aggregated robust_ewma_blend (default). · derived robust_ewma_blend on the derived series; per-device when the algorithm diverges (sleep stages, recovery scores). · frequency windowed_sum with a partial-window guard, then robust centre of the windowed totals.

4 · Data-quality rules · 65 rules, 8 categories — the fool-proof layer

Default stance: quarantine-not-drop · plausibility-gate-before-baseline · idempotent · recomputable-from-raw. Each rule: detect → action → effect-on-baseline → confidence impact. The build guard fails if any metric is left uncovered.

→ resting_hr,hrv_rmssd,spo2,skin_temp_dev,sleep_duration,vo2max_est,gait_speed,bp		Metric values fall on a coarse lattice (integer RHR, 5-min sleep, 1% SpO₂); modal spacing > baseline sensitivityTreat the quantization step as a noise floor: σ = max(observed MAD, step/√12); round deviation thresholds to the lattice → Stops inter-quantum jitter inflating z; stops coarse data hiding real small shifts (conf: cap confidence when effective resolution < metric sensitivity)med
User-entered vs sensor-measured
→ all		Provenance metadata (HKMetadataKeyWasUserEntered, manual flag) or round human numbers (HR 60, 10000 steps) indicate a typed valueTag manual entries; exclude from sensor baselines (or a separate manual track) — a typed value must never set a sensor metric's baseline → Stops a single guessed value anchoring the baseline (conf: mark contaminated if manual fraction high)high
Sustained regime change vs transient outlier
→ resting_hr,hrv_rmssd,skin_temp_dev,spo2,sleep_duration,bp,cgm_tir		A multi-day sustained level shift (illness, pregnancy, altitude move, new medication) via change-point/CUSUM — not a single-day spikeTrigger baseline re-segmentation (new epoch) rather than clipping each day as an outlier; surface as a state change (Doc 05) → Avoids both weeks-long lag (suppressed) and slow poisoning of the old baseline (conf: hold steady, flag the epoch boundary, raise after re-stabilisation)high

Non-random self-measurement bias
→ bp,spo2,hrv_rmssd,cgm_tir,cgm_variability		User-initiated spot metrics (BP, manual SpO₂, on-demand HRV) cluster with state (only when symptomatic/post-exercise) vs passive coverageWeight by representativeness; prefer passive continuous streams for the baseline; down-weight self-selected spot checks → Stops the baseline skewing toward the conditions the user chooses to measure in (conf: lower when sparse + state-correlated)med
Seasonal/circadian drift vs trend
→ resting_hr,hrv_rmssd,skin_temp_dev,sleep_duration,steps,mvpa,vo2max_est		Slow periodic components (annual temperature/daylight on RHR/HRV/sleep; weekday-vs-weekend) detected by seasonal decompositionDe-seasonalise / model day-of-week & season before trend detection; don't attribute predictable swings to baseline drift → Stops the EWMA chasing seasonal cycles into spurious 'improving/worsening' trends (conf: neutral; annotate the seasonal component)med

→ resting_hr,hrv_rmssd,vo2max_est,bp,night_hr_hrv_recovery		Persistently extreme yet self-consistent values (RHR 32, HRV 200ms, VO₂max 80, valid hypertensive BP) that population thresholds would clip, corroborated by stable history + cross-metric coherenceUse PERSONALISED not population bounds once individual history corroborates; don't clip a true tail toward the population mean → Stops aggressive population clipping miscalibrating an athlete's/hypertensive's deviation scores (conf: maintain confidence when individually corroborated)med

5 · Estimator & operational hazards · 23 — even with perfect data

Distinct from data-quality: ways the robust+adaptive statistic and the runtime that serves it can mislead even when every input is clean.

Two safety guardrails (highest stakes)
  • Baseline normalises a pathological-but-stable value — personal μ sits in a clinically abnormal range though personally stable (chronically high resting HR / low SpO₂ / high BP) → DUAL-TRACK — personal-relative z AND absolute clinical guardrails; surface 'your normal is outside the population-healthy range'; personalization must never suppress an absolute red-flag (Doc 05 early-warning)

7 · Identified gaps

  • No live Terra/HealthKit/vendor schema is pinned here — the source paths are illustrative and must be reconciled against current API versions before production.
  • The robust+adaptive formula params (windows, half-lives, winsor %) are expert-priors, not yet calibrated against labelled data (Doc 14).
  • Conditioned baselines (per-device, per-context) multiply state — a device/context registry + storage model is specified but not built.
  • Identity / shared-device disambiguation needs a real biometric-consistency model, not just a flag.
  • Cross-metric coherence checks need the full physiological constraint set encoded as executable assertions.
  • The personal-baseline math currently lives as Doc 03 §2b (κ_resp, 30-day) — this pipeline proposes the robust/adaptive upgrade and a re-baselining (change-point) mechanism that the engine does not yet implement.
